# ship-pr: PR作成からマージまでの一括実行

このスキルは、ローカルの変更を GitHub の Pull Request にし、CI が通るところまで
（指示があればマージまで）面倒を見るための手順をまとめたものです。CLAUDE.md の
「リポジトリ内のコミットメッセージ・コメント・ドキュメントは日本語が基本」という方針に
従い、PRのタイトル・本文・コミットメッセージは日本語で書きます。

このスキルはあくまで手順書であり、実際のPRの世話（マージコンフリクト解消・CI red対応・
レビュー対応・Claude Approvalsチェック対応など）は、システムプロンプトに定義されている
「Driving a PR to green」節のルールに従うこと。このSKILL.mdはそれを上書きしない。

## いつ「マージまで」やるか

- `/ship-pr` をコマンドとして直接叩いた場合（例: `/ship-pr`、`/ship-pr このブランチで`）は、
  マージまでをデフォルトとする。ステップ4・5・6まで実行する。ただし引数で
  「PRだけ作って」「マージはしないで」のように明示的に除外されている場合はステップ3で止める。
- コマンドではなく会話の自然文で依頼された場合（例:「PRを作って」）は、指示文に「マージ」
  「マージまで」「マージして」のように、マージを明示的に含む言葉があるときだけ
  ステップ4まで実行する。「PRを作って」「PR出して」とだけ言われた場合はステップ3
  （PR作成）で止め、マージはしない。
- 迷ったら AskUserQuestion で確認する。

## 手順

### 1. 変更内容の確認

- `git status` / `git diff` / `git log <base>..HEAD` で、現在のブランチに
  未プッシュのコミット・未コミットの変更が何かを把握する。
- 未コミットの変更がある場合は、それを勝手にコミットしない。ユーザーに
  「コミットしてよいか」を確認する（このリポジトリの CLAUDE.md やシステムプロンプトの
  git 運用ルールにある通り、明示的な依頼があるときだけコミットする）。
- 現在のブランチに base ブランチ（通常 `main`）に対する差分が無ければ、PRを作る
  意味がないのでユーザーに伝えて止まる。

### 2. PRテンプレートの確認

- `.github/pull_request_template.md`（または `.github/PULL_REQUEST_TEMPLATE/`、
  ルート直下の `PULL_REQUEST_TEMPLATE.md`）があれば読み、その見出し構成に沿って
  本文を埋める。テンプレートの指示文（HTMLコメントなど）は本文には残さず、
  実際の変更内容で置き換える。
- テンプレートが無ければ、変更内容から自然な本文（概要・変更内容・動作確認など）を書く。
- 本文の末尾には、その時点でシステムプロンプトが指定している attribution フッター
  （PR description 用のもの）を付ける。

### 3. PR作成

- `mcp__github__create_pull_request` で PR を作成する（owner/repo はこのブランチの
  リモートから判断する。通常 `head` は現在のブランチ、`base` はリポジトリのデフォルト
  ブランチ）。
- 作成した PR の URL をユーザーに伝える。
- 上記「いつ『マージまで』やるか」の判断でマージまで進めない場合は、ここでステップ4
  以降は行わずに終了する。

### 4. CI監視とグリーン化（マージまで進める場合のみ）

- `mcp__Claude_Code_Remote__subscribe_pr_activity` でこのPRのイベント購読を開始する。
- 以降のCI失敗・マージコンフリクト・レビューコメントへの対応は、システムプロンプトの
  「Driving a PR to green」節のルール（フレーク判定・re-run は1回まで、他PRの失敗の
  切り分け、Claude Approvals チェックの扱いなど）に従う。このSKILL.mdでは手順を
  重複して書かない。
- CIが継続的に確認できるよう、`mcp__Claude_Code_Remote__send_later` で1時間後を目安に
  自己チェックインを1件仕込んでおく（システムプロンプトの該当ルール通り）。
- 購読した後は一旦ターン（応答）を終える。以降はイベント／チェックインで再開する。

### 5. マージ

以下がすべて揃って初めてマージする。どれか欠けていれば理由をユーザーに伝えて止める
（勝手にスキップやリトライ回数を増やして押し切らない）。

- CIがそのPRの最新コミットで全てグリーン
- ベースブランチとのマージコンフリクトが無い
- 未解決のレビューコメント・changes-requestedなレビューが無い
- リポジトリが Claude Approvals チェックを使っている場合、それも通過している

条件を満たしたら `mcp__github__merge_pull_request` でマージする。マージ方法
（merge/squash/rebase）はリポジトリの慣習・PRテンプレートの指示があればそれに従い、
不明なら squash がデフォルトとして無難。

### 6. 後片付け

- マージ後、`mcp__Claude_Code_Remote__unsubscribe_pr_activity` で購読を解除する。
- 予約していたチェックイン（`send_later`）が残っていれば `delete_trigger` で消す。
- マージ結果（PRのURL、マージコミット）をユーザーに報告する。
